A. VERIFIED FROM REPOSITORY
- dist/index.html and backend/src/contact.mjs require name/band, email, service
  and message. Service has a default selection; the server validates it. Track
  count is optional, 1-60 when supplied. A Turnstile token is required separately.
- dist/assets/theme.js saves asmixes-theme after a choice. No application expiry
  or network transmission of the value exists. Choosing System stores "system";
  clearing browser site data removes the saved value.
- contact.mjs computes HMAC-SHA-256 over the UTC day number and IP with a Worker
  secret. The daily-changing identifier is pseudonymous, not anonymous; the
  secret itself does not rotate daily. Raw IP also keys the separate edge limiter.
- D1 contact_limits has key, count, expires_at. Per-IP keys include the 10-minute
  window and HMAC; global keys contain the daily bucket. These records contain no
  enquiry fields. Per-identifier expiry is the window end; global expiry is the
  daily boundary. The public scheduled handler calls cleanup hourly at minute 23,
  deleting at most 500 expired rows per invocation. Expiry is not physical erasure.
- The browser sends JSON to the Worker. Siteverify receives token and secret, not
  enquiry fields or the remoteip parameter. Resend receives the enquiry fields,
  fixed sender, private configured recipient and reply-to. The public contact
  handler has no content logging or additional message destination. Worker error
  logs elsewhere contain generic portfolio failure/cleanup messages, not bodies.
- Public portfolio API/media use Cloudflare; read endpoints also use edge limits.
  The separate private admin flow uses Cloudflare Access/JWKS and stores portfolio
  metadata/media in D1/R2. That is not an extra enquiry-email forwarding service.
- No additional public tracking pixel, embedded third-party content, analytics
  beacon, log export or browser-storage writer was found in public source/config.
  Turnstile loads dynamically on the homepage. The privacy page loads only the
  existing theme/navigation scripts. Dashboard features remain separate evidence.

PROPOSED LEGITIMATE-INTEREST ASSESSMENT - FOR OWNER REVIEW
Purpose: protect enquiry availability and delivery capacity against plausible
spam, automated submissions and excessive requests. No confirmed attack is assumed.
Evidence to record: ordinary traffic, provider/email quotas, plausible abuse paths,
false-positive reports and why each layer materially addresses those risks.
Necessity: edge limits bound load; D1 counters enforce durable sending caps;
Turnstile adds automated-submission screening. Assess whether their combination,
thresholds and loading Turnstile before form interaction are proportionate.
Compare less intrusive choices: direct-email-only contact, basic validation,
honeypots, lower-volume limits, or challenge-on-interaction. Document effectiveness,
accessibility and trade-offs rather than assuming every alternative is inadequate.
Safeguards: daily-changing HMAC identifiers instead of raw IP in D1, ten-minute
and daily windows, bounded scheduled cleanup, no message/contact details in
counters, and direct email as an alternative. Raw IP remains in edge/provider
processing; pseudonymisation and expiry do not eliminate privacy impacts.
Balance: visitors reasonably expect a working protected form, but shared IPs,
VPNs, assistive technology, disabled scripts and false positives can deny access.
Check rejection rates and accessibility, keep retry messages understandable,
ensure the email alternative is usable, and minimise unnecessary signal collection.
Review thresholds, cleanup backlog and provider purposes periodically and after
material changes or complaints. Cloudflare's separate controller purpose needs
its own consideration. Preventive need can be legitimate, but "just in case"
alone does not prove necessity or proportionality. Owner review and a documented
conclusion are still required; this is not completed legal approval.
